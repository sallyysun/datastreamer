datastreamer · client design

A thin viewer that subscribes, then shows what it's told

One page anyone opens. Each connection subscribes to the symbols it wants; the layout adapts to that subscription. The browser stays a strict viewer — it renders what arrives and runs no estimators. Those live in the C++ consumer devices.

transport · WebSocket topics · trades.equity.<SYM> state · URL-encoded stack · React + uWS

The idea

The TCP broker and the browser's WebSocket are just two transports carrying the same topic pub/sub. We already made the C++ consumer a topic subscriber that pairs two symbols. This design makes the browser the second subscriber on that same model — it picks symbols, the server routes only those topics to it, and the panels rearrange around the choice.

Today the WS side is dumb: every browser is auto-subscribed to one firehose ticks topic and computes a rolling correlation locally. Three things change that: give the WS per-connection subscriptions, drive them from a picker in the UI, and delete the client-side math.

Architecture

What changes — three workstreams

server · uWS

Topic-aware WebSocket

Drop the auto-subscribe to ticks. On open, send a catalog of available symbols. Accept a control message and call ws->subscribe(topic) per symbol. The producer already builds per-symbol ticks — also app.publish() each to its trades.equity.<SYM> topic, so a connection receives only what it asked for.

client · React

Subscription picker + adaptive panels

A row of symbol chips (from the catalog). Toggling one sends a subscribe/unsubscribe and adds/removes its price line. The panels are driven by the subscription: prices for the chosen symbols, a tape of recent ticks, and — once two are selected — a dependence panel. The subscription is encoded in the URL so a link reopens the same view.

client · React

Strict viewer

Delete rollingCorr() and the client-side correlation chart. The browser computes nothing; every number on screen arrived over the wire. Dependence shown in the UI comes only from a real estimator — which means it comes from Phase 2.

The wire protocol

Small and symmetric with the TCP broker's SUBSCRIBE line — just JSON framed over WS instead of newline text.

client → server
// toggle what this connection receives
{ "action": "subscribe",   "topics": ["trades.equity.AAPL", "trades.equity.MSFT"] }
{ "action": "unsubscribe", "topics": ["trades.equity.MSFT"] }
server → client
// on connect: what's available to subscribe to
{ "type": "catalog", "symbols": ["AAPL","MSFT"], "estimates": ["estimates.equity.AAPL_MSFT"] }

// data frames — routed by their own field, rendered as-is
{ "symbol":"AAPL", "price":191.2, "return":0.0004, "timestamp":…, "true_rho_s":0.58 }
// phase 2, from a consumer device:
{ "pair":"AAPL_MSFT", "n":512, "true_rho_s":0.58, "rho":{ "xiao":0.61, "hermite":0.60 } }

Build order

  1. server + client

    Topic-aware WS & picker

    Per-connection subscribe, catalog on connect, per-symbol WS publish. Picker chips, adaptive price panels, URL state. Ship a working raw-data viewer.

  2. client

    Strict viewer cleanup

    Remove rollingCorr and the local correlation chart. Nothing on screen is computed in the browser.

  3. broker + consumer + server

    Live estimates loop

    Broker accepts PUBLISH from consumers; the consumer republishes its ρ̂ to estimates.equity.<PAIR>; the server bridges that topic to WS. The dependence panel lights up with real estimator output vs the true ρ.
